# 對戰與社交成就：驗證設計（第二批，待審）

狀態：設計稿，尚未實作。第一批（成績票修補＋單人成就）另案進行。

## 1. 問題

對戰類 14 個、社交類 7 個成就目前標「需補驗證」，原因：

- 對戰結果（`fin`：分數、準確率、名次、是否通關）由玩家端自己回報，Arena 只檢查數值範圍。
- Arena 不把對戰結果寫進 D1，沒有場次、勝場、對手的紀錄。
- 好友邀請、房主、好友請求方向都沒有留存。
- 其中 11 個成就會給「稱號」，別的玩家看得到，所以不能靠玩家端自報。

## 2. 現況可用的東西

- Arena 的 `auth` 訊息已經把座位對應到 `players.id`（pid），並且拿得到 `env.LB`（D1）。
- `judge(song, d, log)` 能從逐拍紀錄重算準確率、分數、連擊、評級。
- 第一批會讓紀錄帶「護盾擋下的漏接」（0）和星星時間區段，並提供生命值重算。
- `fships (a, b, ts)` 有好友成立時間，但沒有記誰發出請求。
- `/fr/invite` 經 Hub 推送邀請，有效期 `INV_TTL`，沒有寫入 D1。

## 3. 做法

### 3.1 對戰結果改由伺服器重算

1. 玩家端送 `fin` 時附上逐拍紀錄（通關附完整紀錄；倒下附到倒下為止的部分紀錄），以及星星時間區段。
2. Arena 對每個已認證的座位：
   - 通關：`judge()` 重算準確率、分數、最大連擊、全連擊。
   - 倒下：用生命值規則檢查「確實會在最後一拍歸零」。
   - 對戰專用修正：衝刺段（`DU.sprint`）分數 ×2，所以每拍分數上限放寬 2 倍。牽制（bump／shrink／fog）不影響紀錄格式。
3. 名次一律用重算後的分數排。畫面上的頒獎台也改用同一份結果，避免「畫面第一、紀錄第二」。
4. 沒附紀錄、紀錄不合規、或沒認證的座位：這一局對該座位記為「無效」，不給任何對戰成就，也不算進別人的「有效對手」。

### 3.2 有效場

一局要同時滿足才寫入：

- 至少 2 個有效座位，pid 各不相同。
- 從開局到結束的時間 ≥ 該曲該難度的最短長度（同排行榜的票齡檢查）。
- 回合由 Arena 自己的 `phase` 流程走完（不是玩家端宣告結束）。

### 3.3 資料表（只新增）

```
duels  (id PK, ts, song, d, kind, host, seats, valid)
        kind：'qm' 快速配對／'room' 私人房；host：房主 pid；seats：座位數；valid：有效座位數
duelp  (did, pid, place, acc, score, fc, ok, late, PK(did, pid))
        late：90% 處的名次（給「終章逆轉」）
invs   (frm, "to", ts, PK(frm, "to"))        邀請成功（對方真的進房）
fships 加一欄 by：發出好友請求的那一方（舊資料為 NULL）
```

- 回合結束時 Arena 一次 `batch` 寫入，再替每位有效玩家跑 `achRecalc`，新成就經 WebSocket 推回。
- 玩家刪除帳號時 `duelp`、`invs` 的列一起刪；`duels` 不含個人資料，可留。

### 3.4 防刷

帳號是免費的（隨機金鑰＋暱稱），一個人開兩台裝置互打無法根絕，只能提高成本：

| 規則 | 擋什麼 |
| --- | --- |
| 有效對手必須有 ≥3 首不同歌的排行成績 | 隨手開的小號 |
| 對同一位對手，每天最多計 3 勝 | 兩個帳號互刷勝場 |
| 對手必須通關或合法倒下，且命中 ≥30% 的拍 | 對手掛機送勝 |
| 不用 IP 判斷 | 同一個 Wi-Fi 的朋友聚會是主要玩法，不能誤殺 |
| 場次類（熱身賽、擂台常駐、身經百戰）每天最多計 30 場 | 用最短的歌洗場次 |

### 3.5 各成就定義

對戰：

| 成就 | 定義 |
| --- | --- |
| 初次交手／熱身賽／擂台常駐／百戰 | 有效場 1／10／50／200 場（自己是有效座位） |
| 首勝／初露鋒芒／凱旋曲／常勝樂章 | 有效場第 1 名 1／10／50／200 次，受「同對手每日 3 勝」限制 |
| 同台 | 有效座位 ≥4 的一場 |
| 再會 | 和同一位玩家有 3 場有效場 |
| 知音 | 結束時和任一位有效對手準確率（萬分位）完全相同，且雙方都通關 |
| 最終樂章（終章逆轉） | 有效座位 ≥3；90% 處是最後一名，結束是第 1 名（都用紀錄重算） |
| 八方之冠 | 有效座位 = 8，第 1 名 |
| 全場最佳 | 有效座位 = 8，第 1 名且全連擊 |

社交：

| 成就 | 定義 |
| --- | --- |
| 開張／指揮家 | 當私人房房主開局，且該局成為有效場，1／30 場；快速配對不算 |
| 邀約 | 送出邀請後，對方在有效期內認證進入同一房間，1 次 |
| 引路人 | 好友關係由你發出請求（`by`＝你）；對方在成為好友之前沒有任何通關紀錄，之後通關了第 1 首 |
| 好夥伴 | 有效場裡至少 1 位有效對手當時是你的好友，20 場 |
| 合奏團 | 有效座位 ≥4 且其中 ≥2 位是你的好友，10 場 |
| 八音和鳴 | 有效座位 = 8，其他 7 位都是你的好友，1 場 |

### 3.6 相容與上線

- 舊版玩家端的 `fin` 不帶紀錄：照常能玩、畫面照常，只是那一局不計入成就。
- 資料表只新增，舊資料不動。`fships.by` 舊資料是 NULL，所以舊好友不會觸發「引路人」。
- 隱私權政策要補一句「保存對戰結果（名次、準確率、對手關係）」。
- 上線順序：migration → Worker → 網頁版。

## 4. 想請審查的問題

1. 「同對手每日 3 勝」「場次每日 30 場」「對手需有 3 首成績」這三個數字合不合理？會不會誤傷只跟固定朋友玩的玩家？
2. 頒獎台名次改用伺服器重算結果，延遲和失敗時的退路該怎麼做（Arena 重算失敗時照舊用自報值顯示、但不寫入）？
3. Arena（Durable Object）在回合結束時最多要 `judge` 8 份紀錄並寫 D1，有沒有 CPU 時間或一致性的風險？
4. 稱號最高的三個（常勝樂章 200 勝、八方之冠、全場最佳）在這套規則下還有沒有明顯的刷法？
5. 「引路人」的定義會不會被「開小號、加好友、通關一首」輕易刷到？要不要改成只給點數（目前本來就只給點數）就接受？
6. 有沒有漏掉的資料流（重連、中途離開、觀戰、房主換人）會讓有效場的判定出錯？

## 5. 審查後修訂（Fable 獨立審查，2026-11-19）

總評：修改後可動工。以下修訂取代第 3 節中相衝突的內容。

### 5.1 必改

1. **紀錄另開通道**：對戰目前不產生逐拍紀錄（game.js:627 只有一般模式建 `RUN`），Arena 單則訊息上限 512 字元（arena.js:11、236）。對戰也要記逐拍紀錄，並仿 `relayV` 另開「每座位每局一次、上限 16KB」的通道。
2. **分數不能只靠上限檢查**：改過的玩家端每拍都報上限就能贏所有真人。
   - 衝刺 ×2 只放寬最後 20% 的拍（game.js:1098、838），不是全曲。
   - 同一局同一譜，各座位同一拍的分數應該相近：偏離其他座位中位數太多的座位記為「可疑」，可疑的勝場不計。門檻先用現有 `scores.log` 量實際分佈再定。
   - 保留每局第 1 名的紀錄，並加管理員「作廢這一局」的指令。
3. **開局存名單快照**：`startRound` 存 `{座位, pid, 房主, 難度, 對局 id}`。同一 pid 佔多個座位全部無效；開局後才認證的不計；房主以快照為準（現行房主是「在線最小座位」，會變動）。
4. **斷線不能害到對手**：對局中無法重連（arena.js:60），切到背景會直接出局（game.js:725）。快照內的座位只要打過 30% 的拍，離線或出局都算「有效敗方」。刪掉「倒下須在最後一拍歸零」的檢查。
5. **結算當下寫死的欄位**：解除好友會刪掉 `fships` 的列，事後查不回「當時是不是好友」。`duelp` 加 `fr`（有效對手中的好友數）、`cw`（這場是否計勝）、`cg`（這場是否計場），結算時寫入，之後不重算。

### 5.2 建議改（採用）

- 「對手需有 3 首成績」只用在勝場與稱號；初次交手、開張、同台、好夥伴不套用，朋友帶來的新手照算。
- 多人局的勝場：對場上每一位有效對手各扣一次「同對手每日 3 勝」的額度，只要還有一位對手有額度就計勝。「每天」以台灣時間換日。
- 稱號類勝場另加「需勝過 N 位不同對手」（常勝樂章 20 位、凱旋曲 10 位、初露鋒芒 3 位），擋 5 個小號輪流送勝。
- 8 人房條件由「有效座位 = 8」改為「開局 8 人，且有效對手 ≥ 6」，否則有一人斷線或用舊版就全場拿不到。
- 重算放在收到紀錄當下做；結算先存 `ctx.storage`、廣播結果，再用對局 id `INSERT OR IGNORE` 寫 D1，失敗由 alarm 補寫。Arena 不跑 `achRecalc`，改通知玩家端呼叫同步。
- 引路人：在 `becomeFriends`（friends.js:49-52）寫入 `by` 和「對方當時 0 筆成績」的旗標；不靠 `scores.ts`（破紀錄會被覆寫）。
- 邀約：Worker 通知該房 Arena，對方認證進房時直接記成就，不建 `invs` 表。

### 5.3 接受的風險

- 引路人可用小號刷：只給點數。
- 場次類可用小號配最短曲刷：屬於參與型稱號。
- 模擬真人時間差的假紀錄偵測不到：與排行榜相同。
- 舊版玩家端的對局不計入。

### 5.4 與原則的衝突（需使用者決定）

- 「作廢這一局」會收回已發的對戰成就與稱號，和現行「成就一旦取得永不收回」（ach.js:7）不同。建議只對確認作弊的對局開放，由管理員手動執行。
