# 多人模式通訊協定（v2，2～8 人）

舊的雙人對戰（`/new`、`/ws/<房號>`、`Room` 物件）原封不動保留，給還沒更新的舊版 App 用。新版客戶端只用下面的 v2。

## 端點（都要通過現有的 Origin 檢查與 RL 頻率限制）

| 方法與路徑 | 用途 | 回應 |
|---|---|---|
| `GET /m/new?pub=0\|1&max=2..8&di=0..4` | 建立房間（房主之後可改設定；`max` 預設 6，與客戶端一致，見待決事項） | `{code}` |
| `GET /m/rooms?di=-1..4&space=1` | 公開房間列表，最多 30 筆；`di=-1` 不限；`space=1` 只列大廳階段且有空位的 | `{rooms:[{code,host,song,di,n,max,phase,qm}]}` |
| `GET /m/match?di=-1..4&max=2..8` | 快速配對：找條件相符、大廳階段、有空位的快速配對房；沒有就開一間新的 | `{code}` |
| `GET /m/ws/<房號>`（WebSocket） | 進房 | 見下方訊息 |

- 房號格式同舊版（4 碼，`ALPH` 字元），但存在新的 `Arena` Durable Object（`env.ARENA`，wrangler.toml 新增 binding 與 migration `v3`，`new_sqlite_classes = ["Arena"]`）。
- 大廳是新的 `Lobby` Durable Object（`env.LOBBY`，單一實例 `idFromName('lobby')`，同一個 migration `v3`）。Arena 在人數、設定、階段變化時把房間摘要送到 Lobby（`/upsert`、房間空了送 `/remove`）；Lobby 只放記憶體、不寫 storage（DO 重啟後由各 Arena 每 30 秒的刷新補回）；只保留 2 分鐘內有更新的房間。上限 500 間真房：滿了就淘汰人數最少、最舊的公開房，不拒絕新房，`/m/match` 不會因上限回 503。
- 配對預留：`/m/match` 開新房時 Lobby 先放一個佔位房（不列入 `/m/rooms`、不計入 500 上限，約 15 秒沒人連上就消失）。Lobby 另記每間房的「待加入」時間戳（約 10 秒過期），挑房時用「實際人數＋待加入數」判斷空位；玩家真的連上、Arena 回報人數增加後就扣掉對應的待加入數。
- Arena 在 hello 改名時只有本人是房主才更新大廳摘要，且同一房的摘要更新至少間隔 1 秒（節流，最後一次會補送）。房號在第一次 WebSocket 升級時存入 storage，`ctx.id.name` 沒值時用它。
- `di=-1`（不限）配對時優先找人最多的房；建立快速配對新房時難度用 1（普通）。
- 快速配對房（`qm:true`）：曲目由伺服器從 `CHARTS` 的 key 隨機挑；沒有房主設定，人到齊自動開始：人數達 `max` 時 3 秒後開始；人數 ≥ 2 時，從「第 2 人」就緒起最多等 15 秒就開始。開始前倒數資訊放在 `room.auto`。
- 一局結束回大廳後，快速配對房不會自動重新倒數：所有人 `back` 變 false，要有 ≥ 2 位玩家送出 `again`（新加入的玩家一進房就算就緒）才開始倒數，滿房（全員就緒且達 `max`）3 秒，否則 WAIT 秒。開始時房內所有人都會進局（沒按 `again` 的也包含）。
- 一般房間（`qm:false`）：房主（目前在房內 `i` 最小者）決定曲目、難度、公開與否、人數上限、是否投票選曲；所有人按準備且人數 ≥ 2 才開始；有人離開（大廳階段）後，若剩下 ≥ 2 人且全員已準備，立刻開始。

## 客戶端 → 伺服器（全部欄位重新驗證、夾範圍，只轉送重建過的欄位）

| t | 欄位 | 規則 |
|---|---|---|
| `ping` | `c` | 回 `pong {c,s}` |
| `hello` | `name` | 大廳階段；清理同舊版 cleanName，再過 names.js 的不雅字詞檢查（若有提供可用函式） |
| `cfg` | `song`(key)、`di`(0..4)、`pub`(bool)、`max`(2..8，不得小於目前人數)、`vote`(bool) | 只限房主、大廳階段、非快速配對；節流 400 ms；`song` 必須是 CHARTS 裡的 key；改曲或難度時所有人取消準備 |
| `vote` | `song`(key) | 大廳階段且 `cfg.vote`；每人一票可改 |
| `ready` | `v`(bool) | 大廳階段 |
| `st` | `s,c,l,r,j` | 比賽中且未完成；存成此玩家最新狀態（分數倒退忽略；一次增加超過 30,000 則夾成上次＋30,000）；距上次廣播 ≥ 250 ms 就廣播 `board` |
| `atk` | `k`∈bump/shrink/fog | 比賽中；每人 2 秒一次；目標＝分數排在自己正前方、尚未完成的玩家；自己是第一名時給第二名 |
| `fin` | `s,ok,acc,rank,mc` | 比賽中、每回合一次；`acc` 為 0～1（伺服器僅夾範圍、不縮放）；所有在線玩家都完成時廣播 `res` 並回到大廳 |
| `again` | — | 同舊版：回合已結束或卡住超過 20 秒時回大廳；快速配對房在大廳階段送出表示「回到房間就緒」（`back`） |
| `auth` | `pk` | 讓房間知道這個座位是哪個帳號（只存在伺服器的 attachment，`pid` 不會出現在任何送給其他玩家的訊息）；每個 socket 最多試 3 次；成功後回 `rel` 給自己，並更新其他已登入座位的 `rel` |
| `rel` | — | 間隔 800 ms；回 `rel` |
| `fadd` | `i`(0..7 整數，非整數忽略) | 對該座位送好友邀請（共用 friends.js 的 `friendRequest`，與 `/fr/add` 相同；對方已先邀請則直接成為好友）；任一方封鎖時回 `x`；間隔 600 ms |
| `say` | `k`(0..63 整數) | 大廳階段的快速短語，只傳索引（文字在用戶端的清單，只能往後加）；每人 2.2 秒一次；封鎖了發言者的人收不到 |

投票選曲開始時，曲目＝票數最高者（同票隨機；沒人投就用房主設定的曲目）。

## 伺服器 → 客戶端

- `room {code, you, host, players:[{i,name,ready,back,vote}], cfg:{song,di,pub,max,vote,qm}, votes:{key:n}, phase:'lobby'|'play', auto:null|{at}}`，`i` 為 0..7；`back`（bool）表示玩家已回到房間就緒，只有快速配對房有意義（一般房恆為 true）
- `start {at, seed, song(key), di, n}`（`at` = 伺服器時間 +4500 ms）
- `board {p:[[i, s, c, l, j, fin(0/1), ok(0/1)], …]}`；`ok` 為 0 只有「已 fin 且 ok:false（出局）」，其餘為 1
- `atk {from, k}`（只送給目標）
- `res {r:[{i, name, s, ok, acc, rank, mc}, …]}`（依分數高到低；出局者排在完成者之後）
- `left {i}`
- `rel {r:{seat:'f'|'o'|'i'|'b'|'n'}}`：自己和其他已登入座位的關係（好友、已邀請、對方邀請我、我封鎖對方、無）；未登入的座位不列出；對方封鎖我不會被揭露
- `fadd {i, r:'f'|'o'|'x'}`：成為好友／已送出邀請／無法送出（含任一方封鎖）
- `say {i, k}`
- 房間滿了：WebSocket 升級回 409；房號不存在：404。

## 防護（沿用舊版做法）
每個 socket 的 token bucket、訊息上限 512 bytes、閒置 75 秒踢除、房號只有經 `/m/new` 或 `/m/match` 保留後才能加入、所有數字夾範圍、所有名稱清理。比賽中 `st` 的分數若倒退就忽略那則訊息；若一次增加超過 30,000，改成夾在「上次＋30,000」（不整則丟棄，避免排行榜永久凍結）。

## 補充
- 比賽中有人離線：廣播 `left {i}`；若剩下的在線玩家都已完成，立即廣播 `res`（離線且未完成者以 ok:false、最後一次分數排在最後）並回到大廳。
- 比賽中有人要進房：WebSocket 升級回 423。

## 好友短語（friends.js，不經房間）
（舊版 App 使用；新版改用 /fr/msg，仍接收 fsay）`POST /fr/say {pk, id, k}`：只限好友、`k` 為 0..63，經 Hub 推送 `fsay {from:{id,name}, k, ts}` 給對方所有在線裝置；不儲存，對方不在線就收不到（回 `delivered:false`）；同一對 3 秒一次、每人每分鐘 20 則。

`POST /fr/msg {pk, id, text, k?}`：自由文字，只限好友。順序：好友關係 → 頻率（Hub `/i/rate`，同一對 1 秒一次、每人每分鐘 20 則）→ 清理（NFC、換行變空白、去控制字元但保留 ZWJ、最多 60 字）→ 過濾（`names.js msgProblem`：比對前先去掉隱形字元與變音符號；中文詞任意位置、英文逐字並合併「f.u.c.k」；網址、電子郵件、IG/LINE/Discord/微信等帳號寫法、9 位以上數字）。被擋回 `{error:'filtered', why:'words'|'link'}`，不儲存。通過後存入 `fmsgs`（保存 7 天），經 Hub `/i/dm` 推送：auth 帶 `v:2` 的新版收 `fmsg {from:{id,name}, m:{id,text,ts}}`；舊版若訊息帶 `k`（快速短語索引）改收 `fsay`，否則不算送達。回 `{ok, m, delivered}`。

`POST /fr/msgs {pk, id}`：與某位好友最近 50 則訊息，只含 7 天內且在「這次成為好友之後」的訊息，`[{id, me, text, ts}]` 由舊到新。`/fr/list` 的每位好友多一個 `lm {id, me, text, ts}`（同樣範圍的最後一則）。

`POST /fr/report {pk, id, mid?}`：有 `mid` 時該則必須是對方傳給自己的訊息，內容副本存入 `freports`；沒有 `mid` 時（檢舉玩家）必須是好友或對方 7 天內傳過訊息給自己，副本為對方最近 20 則訊息。每人每天最多 30 筆；同一對象的玩家檢舉會更新副本。管理：`/lb/admin {op:'dmreports'}`。

刪除好友或封鎖時訊息不刪除（雙方都讀不到，只供檢舉），到期由每日 cron（`friendSweep`）刪除；檢舉保存 1 年。刪除線上資料時，雙方訊息與相關檢舉立即刪除。
